HOW EVERY REFERENCE WAS RESOLVED
--------------------------------------------------------------------------------
1. ADDRESS MAP.  The ELF has exactly one PT_LOAD: vaddr 0x0f900000, p_offset
   0x8000, filesz 0xe93d8, memsz 0xfe53c.  Therefore
       file_offset = vaddr - 0x0f900000 + 0x8000
   and 0x8000..0xf73d8 of the file is the only file-backed code/data.
   (PH1 at 0x1000 is PT_NULL - not a segment.  PH2 at 0x8ce80 is
   PT_ARM_EXIDX, vaddr 0x0f984e80, which maps consistently with the formula
   above: 0x0f984e80-0x0f900000+0x8000 = 0x8ce80.)

2. FUNCTION BOUNDARIES.  The image is stripped (no symbol table, no section
   headers).  A function start is taken as the next address that is either
   (a) the target of a `bl`, or (b) a `push {... lr}` prologue.  A function
   ends at the next such address; the `pop {..., pc}` / `bx lr` epilogues are
   marked in the listing.  Where a function ends with a `bl <noreturn>`
   (e.g. 0x0f93c1dc, the assert/panic helper) that trailing call is kept
   inside the function.  A trailing `bl` to a noreturn helper is the only
   code after the last `pop {..,pc}`.

3. PC-RELATIVE / CONSTANT RESOLUTION (exact method):
   a) LK builds every 32-bit constant with a register pair, never with an
      absolute literal pool.  Two encodings are used and BOTH are paired
      here:
        - `mov  rD,#lo16` + `movt rD,#hi16`   (lo16 as an ARM rotated imm)
        - `movw rD,#lo12` + `movt rD,#hi16`
      Pairing rule: scan forward from the low-half instruction for the first
      `movt` writing the SAME register; the intervening instructions must be
      only movw/movt, otherwise the pair is rejected.  The reconstructed
      value is printed in the comment of BOTH instructions.
   b) `ldr rX,[pc,#imm]` literal pools: the pool word is read at
      (addr+8)&~3 + imm and printed as "literal pool @0x... = 0x...".
      LK's *code* uses these only for branch/jump-table data; all hardware
      addresses come from (a) or from (d).
   c) `str/strh/strb rS,[rB,#disp]`: the destination is resolved as
      value(rB)+disp whenever value(rB) is a known absolute address.
      For that, a per-function constant propagation is run (movw/movt pairs,
      mov #imm, add/sub #imm, ldr from a literal pool, and the structure
      model of section 4).
   d) HARDWARE BASES THAT LIVE IN STRUCTURES.  The CORE/HC bases are not
      immediates; they are copied out of a platform descriptor at runtime.
      They were resolved by following the data flow, and the resulting
      structure map is reproduced in the header of each file:
        plat_struct (built on the stack by target/msm8992_alphap/init.c):
            +0x00 u8  = 1              (controller/slot id)
            +0x04 u32 = 0xaa           (quirks)      [2nd attempt: 0xfd]
            +0x08 u32 = 0xf9824900     (hc_mem  = SDHCI HC block)
            +0x0c u32 = 0xf9824000     (core_mem= MCI/SDHCI CORE block)
            +0x10 u16 = 2              (bus width)
            +0x14 u32 = 0x0b71b000     (ioaddr / DLL base)
            +0x18 u32 = 0
            +0x1c u32 = *(0x0f9fd598)  (not copied: memcpy size is 0x1c)
          the 0x1c-byte descriptor is memcpy'd to host+0xf8, so:
            host+0xf8 = 1, host+0xfc = 0xaa, host+0x100 = 0xf9824900 (HC),
            host+0x104 = 0xf9824000 (CORE), host+0x108 = 2,
            host+0x10c = 0x0b71b000, host+0x110 = 0
          and the "plat" object handed to sdhci_msm_init is built as:
            plat+0x00 = 0xf9824000 (CORE)   plat+0x04 = 0xaa (quirks)
            plat+0x08 = 0   plat+0x0b = 1 (u8)  plat+0x0c = 0 (u8)
            plat+0x10 = <ptr>  plat+0xe8 = <flags>
          The global `dev` (0x0f9fd588) points at the same "host" object
          (init_entry returns it), hence dev+0x30 = plat and *plat = CORE.
   e) STRING REFERENCES: every movw/movt pair whose value is a printable
      string address is printed as  string "...".

4. FORMAT
   <addr>  <8 hex bytes in memory order>  <mnemonic> <operands>   ; <comment>
   The byte column is the 4-byte instruction word in little-endian memory
   order.  "WRITE 0x........" marks a resolved store destination.

5. LIMITS / HONEST CAVEATS
   - The image is stripped: no symbol names, no DWARF.  Function names in
     this report are the names given in the task brief, or descriptive
     labels derived from the strings/arguments inside the function.
   - Register values loaded from memory are opaque unless the memory
     location is covered by the structure map of section 3(d).
   - SDHCI/Qualcomm register *names* are only asserted where the task brief
     or the binary itself fixes them; elsewhere only the offset is given.
   - The linker places literal pools and .rodata inline in the code stream;
     where the linear disassembly walks over such data it is marked
     ".byte".
